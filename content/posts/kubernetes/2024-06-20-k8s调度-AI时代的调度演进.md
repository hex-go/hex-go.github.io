# 重要

AI 训练任务对调度器提出了新需求：GPU 拓扑感知（同一任务的 GPU 要靠近彼此）、Gang 调度（所有 Pod 必须同时运行）、NUMA 对齐（CPU 和 GPU 在同一 NUMA 节点）。传统调度器逐个 Pod 调度的模式无法满足这些需求，催生了 Volcano、Coscheduling 等扩展方案。

---

## 1. GPU 拓扑感知

### 1.1 问题

分布式训练（如 PyTorch DDP、NCCL all-reduce）中，GPU 之间的通信带宽决定了训练效率：

| GPU 拓扑 | 带宽 | 延迟 |
|---------|------|------|
| 同 PCIe Switch | 全速（如 600 GB/s NVLink） | 极低 |
| 同节点跨 PCIe | 通过 CPU QPI/UPI | 中等 |
| 跨节点 | 通过网络（RDMA/InfiniBand/以太网） | 高 |

{{< keypoint >}}
如果调度器将同一训练任务的 8 个 GPU Pod 随机分散到 8 个节点，NCCL 通信跨网络走，训练速度可能下降 50% 以上。理想情况：同一任务的 GPU 尽量靠近（同节点、同 PCIe Switch、同 NVSwitch）。
{{< /keypoint >}}

### 1.2 调度器如何感知

**节点标签暴露 GPU 拓扑：**

```yaml
# NVIDIA GPU Operator 为节点打标签
metadata:
  labels:
    nvidia.com/gpu.product: NVIDIA-A100-SXM4-40GB
    nvidia.com/gpu.count: "8"
    nvidia.com/gpu.memory: "40960"  # MiB
    nvidia.com/gpu.family: ampere
```

**Pod 通过 nodeAffinity / topologySpreadConstraints 约束：**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-training
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nvidia.com/gpu.product
            operator: In
            values: ["NVIDIA-A100-SXM4-40GB"]
```

## 2. Gang 调度（Coscheduling）

### 2.1 问题

AI 训练任务通常是一组 Pod（如 Parameter Server + Workers），需要**同时运行**。传统调度器逐个调度 Pod，可能出现 Worker Pod 都 Ready 了但 PS 还在 Pending——训练无法开始，Worker 空耗 GPU。

### 2.2 Gang 调度原理

Gang 调度器将一组 Pod 视为一个 Gang，"要么全调度，要么都不调"：

{{< diagram >}}
传统调度：
  Pod-1 Ready → Pod-2 Pending（资源不足）→ Pod-1 空转等待

Gang 调度：
  Pod-1, Pod-2, Pod-3 同时等待 → 所有 Pod 资源满足后一次性分配
  → Gang Ready → 启动训练
{{< /diagram >}}

### 2.3 Volcano Scheduler

Volcano 是 CNCF 的批量调度项目，实现了 Gang 调度：

```yaml
apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: tf-job
spec:
  minAvailable: 4     # 至少 4 个 Pod 同时就绪才开始
  tasks:
  - replicas: 2
    name: ps
    template:
      spec:
        containers:
        - name: ps
          image: tensorflow/tensorflow:2.4
          resources:
            requests:
              nvidia.com/gpu: 0     # PS 不需要 GPU
  - replicas: 2
    name: worker
    template:
      spec:
        containers:
        - name: worker
          image: tensorflow/tensorflow:2.4
          resources:
            requests:
              nvidia.com/gpu: 1     # 每个 Worker 需要 1 GPU
```

## 3. NUMA 感知调度

### 3.1 问题

多 NUMA 节点服务器上，CPU 访问本地 NUMA 节点的内存延迟远低于远端：

```text
Server: 2 sockets, 4 NUMA nodes
  NUMA 0: CPU 0-7, GPU 0, Memory 0
  NUMA 1: CPU 8-15, GPU 1, Memory 1
  ── NUMA 间互访延迟 = 本地延迟 × 2-3
```

如果 GPU Pod 的 CPU 在 NUMA 0 但 GPU 在 NUMA 1，每次 CPU-GPU 数据传输都跨 NUMA，延迟翻倍。

### 3.2 K8s 1.26+ 的 NUMA 感知

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: numa-pinned
spec:
  containers:
  - name: app
    resources:
      limits:
        memory: "32Gi"
        nvidia.com/gpu: "1"
        cpu: "8"
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
```

**NodeResourceTopology（K8s 1.26+ CRD）：**

```yaml
apiVersion: topology.node.k8s.io/v1alpha1
kind: NodeResourceTopology
metadata:
  name: node-1
topologyPolicies: ["SingleNUMANodePodLevel"]
zones:
- name: node-1-zone0
  type: Node
  resources:
  - name: cpu
    capacity: "16"
    allocatable: "12"
  - name: memory
    capacity: "64Gi"
    allocatable: "48Gi"
```

## 4. 多任务调度（Job Queue）

AI 集群通常同时运行多个训练任务。调度器需要管理任务队列：

| 需求 | 说明 | 方案 |
|------|------|------|
| 公平调度 | 小任务不被大任务饿死 | Volcano fair-share、Kueue |
| 抢占与排队 | 大任务等待资源时不被小任务抢占 | 优先级 + 队列等待 |
| 弹性训练 | 任务中途增减 Worker 数量 | Elastic Horovod、TorchElastic |
| 多集群调度 | GPU 资源跨集群 | Karmada、Armada |

## 5. Kueue：资源队列管理

Kueue 是 K8s SIG-Scheduling 的资源队列管理项目：

```yaml
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: gpu-flavor
spec:
  nodeLabels:
    nvidia.com/gpu.product: NVIDIA-A100-SXM4-40GB
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: team-a-gpu-queue
spec:
  namespaceSelector: {}
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: gpu-flavor
      resources:
      - name: cpu
        nominalQuota: 100
      - name: memory
        nominalQuota: 500Gi
      - name: nvidia.com/gpu
        nominalQuota: 8
```

## 6. 各调度方案对比

| 方案 | Gang 调度 | GPU 拓扑 | NUMA | 队列管理 | 适用场景 |
|------|----------|---------|------|---------|---------|
| 默认调度器 | ❌ | ❌（需手动 affinity） | ❌ | ❌ | 简单 AI 推理 |
| Volcano | ✅ | ✅ | ✅ | ✅ | 大规模分布式训练 |
| Kueue | ❌ | ❌ | ❌ | ✅ | 多租户 GPU 管理 |
| Coscheduling Plugin | ✅ | ❌ | ❌ | ❌ | 轻量 Gang 调度 |

## 7. 未来方向

| 方向 | 说明 |
|------|------|
| **调度器框架标准化** | Scheduling Framework 成为扩展的标准接口（K8s 1.15+） |
| **GPU 碎片整理** | 类似内存碎片整理，迁移 GPU 使用使拓扑更紧凑 |
| **跨集群 GPU 调度** | 训练任务跨多个 K8s 集群分配 GPU |
| **Spot GPU 抢占** | 类似 AWS Spot 实例，低价 GPU 可被抢占 |
| **动态 MIG 切分** | GPU MIG 实例按需创建/调整，配合调度器实时分配 |
