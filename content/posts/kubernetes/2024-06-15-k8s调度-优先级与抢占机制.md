# 重要

优先级（Priority）决定 Pod 在调度队列中的出队顺序。抢占（Preemption）发生在高优先级 Pod 调度失败时——调度器会驱逐低优先级 Pod 释放资源。抢占不是立即驱逐，而是提名（nominatedNodeName）+ 等待优雅退出后的下一轮调度。

---

## 1. PriorityClass

### 1.1 定义

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "用于核心服务，在资源紧张时优先保障"
```

| 字段 | 说明 |
|------|------|
| `value` | 优先级数值，越大越高。范围：0 ~ 1,000,000,000（10亿） |
| `globalDefault` | 是否作为默认优先级（不声明 priorityClassName 的 Pod 使用） |
| `description` | 描述信息 |

### 1.2 优先级范围

| 范围 | 用途 | 典型值 |
|------|------|--------|
| > 10亿 | Kubernetes 系统 Pod | system-cluster-critical: 2,000,000,000 |
| 1 ~ 10亿 | 用户 Pod | high: 1,000,000 / medium: 100,000 / low: 1 |
| 0 | 默认优先级（未声明 PriorityClass） | — |

### 1.3 使用

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: critical-app
spec:
  priorityClassName: high-priority
  containers:
  - name: nginx
    image: nginx
```

Pod 创建时，`PriorityAdmissionController` 自动将 `spec.priority` 设置为 PriorityClass 的 value。

---

## 2. 优先级如何影响调度

| 阶段 | 优先级的作用 |
|------|------------|
| 入队 | 高优先级 Pod 排在队列前面（`activeQ` 是优先级队列） |
| 调度失败 | 低优先级 Pod 被放在 backoff 队列，高优先级 Pod 可抢占 |
| 抢占 | 调度器寻找可被驱逐的低优先级 Pod 所在节点 |

---

## 3. 抢占机制

### 3.1 什么时候触发

当 Pod 调度失败（所有节点都不满足条件）且 Pod 有优先级时，调度器启动抢占逻辑：

```text
1. Pod P 调度失败
2. 判断 P 是否有优先级？有 → 触发抢占
3. 遍历所有节点，找出可以通过驱逐低优先级 Pod 释放足够资源的节点
4. 选出"牺牲最少"的节点（驱逐最少 Pod 且优先级最低）
5. 将驱逐列表中的 Pod 标记为 Deleting
6. 在 P 上设置 spec.nominatedNodeName = 选中节点
7. P 回到 activeQ，等待下一轮调度
```

### 3.2 nominatedNodeName

抢占发生后，Pod 的 `nominatedNodeName` 字段被设置为目标节点名。**抢占者不会立即被调度**，而是进入下一轮调度周期：

| 场景 | 处理方式 |
|------|---------|
| 驱逐的 Pod 优雅退出完成 | 抢占者被调度到该节点 |
| 驱逐期间出现更合适的节点 | 抢占者可能被调度到其他节点 |
| 更高优先级 Pod 也要抢占同一节点 | 原抢占者的 nominatedNodeName 被清空，让更强者执行抢占 |

### 3.3 抢占约束

| 条件 | 说明 |
|------|------|
| PDB（PodDisruptionBudget） | 不能违反 PDB——如果驱逐会打破预算，该节点不考虑 |
| 只有低优先级 Pod 被驱逐 | 同优先级或更高优先级 Pod 不被驱逐 |
| 优雅退出时间 | 被驱逐 Pod 有 terminationGracePeriodSeconds（默认 30s） |

---

## 4. 非抢占优先级（Non-Preempting Priority）

K8s 1.24+ 支持非抢占优先级：

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-but-no-preempt
value: 1000000
preemptionPolicy: Never   # 不抢占，仅影响调度队列顺序
```

| preemptionPolicy | 含义 |
|-----------------|------|
| `PreemptLowerPriority`（默认） | 允许抢占低优先级 Pod |
| `Never` | 不抢占，只排在高优先级位置等资源释放 |

---

## 5. 优先级与驱逐的区别

| 维度 | 抢占（Preemption） | 节点压力驱逐（Eviction） |
|------|------------------|----------------------|
| 触发者 | kube-scheduler | kubelet |
| 原因 | 高优先级 Pod 调度失败 | 节点资源不足（内存/磁盘） |
| 目标 | 释放资源给待调度 Pod | 保护节点稳定性 |
| 优先级 | 从低到高驱逐 | QoS 从低到高驱逐 |

---

## 6. 实际场景

### 6.1 典型配置

```yaml
# 优先级层次
# system-cluster-critical (2B) > system-node-critical (1B) > high (1M) > default (0)
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: medium-priority
value: 100000
globalDefault: false
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 1
globalDefault: true   # 默认优先级
```

### 6.2 查看 Pod 的优先级

```bash
kubectl get pod <name> -o yaml | grep priority
# priority: 1000000
# priorityClassName: high-priority
```
