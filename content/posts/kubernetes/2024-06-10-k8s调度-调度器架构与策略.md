# 重要

kube-scheduler 是 K8s 的默认调度器，负责为每个 Pod 找一个最合适的节点。核心流程分为三个阶段：过滤（Predicates，找出所有可运行节点）→ 打分（Priorities，选出最优节点）→ 绑定（Bind，写 nodeName）。调度器通过 Informer 监听集群状态、Cache 化加速、Assume 乐观绑定来保证高性能。

---

## 1. 调度器架构

### 1.1 两个控制循环

{{< diagram >}}
第一个循环（Informer Path）：
  监听 Etcd 中 Pod/Node/Service 变化
  → 新 Pod（nodeName 为空）入队
  → 更新 Scheduler Cache（集群状态快照）

第二个循环（Scheduling Path）：
  从调度队列出队 Pod
  → Predicates 过滤（选可运行节点）
  → Priorities 打分（排序选最优）
  → Assume 绑定（乐观更新 Cache）
  → 异步调用 API Server 完成实际 Bind
{{< /diagram >}}

### 1.2 调度队列

| 队列 | 说明 |
|------|------|
| `activeQ` | 等待调度的 Pod（按优先级排序） |
| `unschedulableQ` | 调度失败的 Pod（等条件改变后重新入队） |
| `backoffQ` | 调度失败次数过多的 Pod（退避等待） |

### 1.3 高性能设计

| 设计 | 说明 |
|------|------|
| **Cache 化** | 调度器本地缓存所有 Node/Pod 信息，过滤和打分不需要访问 API Server |
| **Assume 乐观绑定** | 先在 Cache 中标记 Pod 已调度（Assume），再异步写 API Server |
| **无锁化并发** | 过滤和打分以节点为粒度并行执行，不共享锁 |
| **Informer** | 增量监听 API Server，同步周期短 |

## 2. 调度流程

```text
Pod 创建（spec.nodeName 为空）
  ↓
调度队列（activeQ）
  ↓
Predicates 过滤阶段：逐个节点检查是否满足条件
  ↓ 得到候选节点列表
Priorities 打分阶段：对候选节点打分（0-10分）
  ↓ 选出最高分节点
Assume 阶段：乐观更新 Cache 中的 Pod.nodeName
  ↓
Async Bind：异步调用 API Server 的 Bind 接口
```

## 3. Predicates（过滤策略）

过滤阶段从集群所有节点中筛出可以运行该 Pod 的节点。默认策略分为三类：

### 3.1 GeneralPredicates（通用过滤）

| 策略 | 说明 |
|------|------|
| `PodFitsResources` | 检查节点剩余 CPU/内存是否满足 Pod 的 requests |
| `PodFitsHost` | 检查 Pod 的 spec.nodeName 是否匹配节点名 |
| `PodFitsHostPorts` | 检查 Pod 申请的宿主机端口是否冲突 |
| `PodMatchNodeSelector` | 检查 Pod 的 nodeSelector / nodeAffinity |

### 3.2 Volume 相关过滤

| 策略 | 说明 |
|------|------|
| `NoDiskConflict` | 检查 Volume 是否已被其他 Pod 挂载（如 EBS 不可共享） |
| `MaxPDVolumeCountPredicate` | 检查节点上同类型 Volume 数量是否超标 |
| `VolumeZonePredicate` | 检查 Volume 的可用区与节点可用区是否匹配 |
| `VolumeBindingPredicate` | 检查 PV 的 nodeAffinity（Local PV 必须本节点） |

### 3.3 节点相关过滤

| 策略 | 说明 |
|------|------|
| `PodToleratesNodeTaints` | 检查 Pod 的 tolerations 是否容忍节点污点 |
| `CheckNodeCondition` | 检查节点状态（Ready、DiskPressure、MemoryPressure 等） |
| `CheckNodeMemoryPressure` | 节点内存压力时拒绝调度 BestEffort Pod |
| `CheckNodeDiskPressure` | 节点磁盘压力时拒绝调度新 Pod |

---

## 4. Priorities（打分策略）

打分阶段对过滤后的候选节点进行评分，选出最优节点。得分 0-10。

### 4.1 常用打分算法

| 算法 | 说明 | 计算方式 |
|------|------|---------|
| `LeastRequestedPriority` | 资源使用率越低得分越高 | `(capacity - request) / capacity` |
| `BalancedResourceAllocation` | CPU 和内存使用率差异越小越好 | `1 - abs(cpu% - mem%)` |
| `SelectorSpreadPriority` | Pod 尽量分散在不同节点/可用区 | 同 Service/RC 的 Pod 数量越少得分越高 |
| `NodeAffinityPriority` | nodeAffinity 匹配度越高得分越高 | preferred 规则匹配数 |
| `TaintTolerationPriority` | toleration 匹配越精确得分越高 | 规则匹配计数 |
| `ImageLocalityPriority` | 镜像已在节点上得分高 | 已存在镜像的大小之和 |
| `InterPodAffinityPriority` | Pod 间亲和性规则匹配度 | 匹配的 Pod 数量 |

### 4.2 LeastRequestedPriority 示例

```text
节点 A：已用 60% CPU，40% 内存 → 得分 = (40% + 60%) / 2 * 10 = 5
节点 B：已用 20% CPU，20% 内存 → 得分 = (80% + 80%) / 2 * 10 = 8
→ 节点 B 得分更高，优先调度
```

## 5. Extended Resource 调度

K8s 对 GPU 等硬件资源使用 Extended Resource 机制：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  containers:
  - name: cuda-app
    image: nvidia/cuda:11.0
    resources:
      limits:
        nvidia.com/gpu: 1
```

| 关键点 | 说明 |
|--------|------|
| 资源名 | 自定义格式，如 `nvidia.com/gpu` |
| 调度计算 | 调度器让可用量直接减 Pod 声明的数量 |
| 节点上报 | 通过 Device Plugin 的 ListAndWatch 汇报可用数量 |
| Node Status | 节点 Capacity 中包含 `nvidia.com/gpu` 字段 |

## 6. 调度器扩展机制

### 6.1 多调度器

可以运行多个调度器（需要自定义 `schedulerName`）：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: custom-scheduled
spec:
  schedulerName: my-scheduler   # 指定自定义调度器
  containers:
  - name: nginx
    image: nginx
```

### 6.2 调度器扩展方式

| 方式 | 说明 | K8s 版本 |
|------|------|---------|
| Scheduler Extender | HTTP Webhook，外部服务决定调度结果 | 1.5+ |
| Multiple Schedulers | 部署多个调度器实例 | 1.6+ |
| Scheduling Framework | 插件化架构，精细控制调度各阶段 | 1.15+ |
