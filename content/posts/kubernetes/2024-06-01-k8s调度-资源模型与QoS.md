# 重要

K8s 资源管理的核心是 requests 和 limits 两个字段。requests 决定调度，limits 决定运行时上限。两者配合 cgroups 实现 CPU/内存的隔离与保障。QoS 类（Guaranteed/Burstable/BestEffort）决定了 OOM 时的杀 Pod 顺序。

---

## 1. 资源模型

### 1.1 requests 与 limits

Pod 中每个容器都可以声明资源需求：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
```

| 字段 | 作用 | 说明 |
|------|------|------|
| `requests` | 调度依据 | 调度器根据 requests 计算节点是否有足够资源 |
| `limits` | 运行时上限 | kubelet 通过 cgroups 限制容器不能超过 limits |
| `requests.cpu` | 调度时的 CPU 保证 | 转换成 `cpu.shares`（按比例分配 CPU 时间） |
| `limits.cpu` | 运行时 CPU 硬上限 | 转换成 `cpu.cfs_quota_us`（绝对上限） |
| `requests.memory` | 调度时的内存保证 | 仅用于调度计算，不硬限制 |
| `limits.memory` | 运行时内存硬上限 | 转换成 `memory.limit_in_bytes`，超限触发 OOM Kill |

### 1.2 CPU 单位

| 写法 | 含义 | 说明 |
|------|------|------|
| `1` | 1 个 CPU | 1 核、1 vCPU、1 超线程 |
| `500m` | 500 millicpu | 0.5 个 CPU（推荐写法） |
| `250m` | 250 millicpu | 0.25 个 CPU |

### 1.3 内存单位

| 写法 | 含义 |
|------|------|
| `64Mi` | 64 mebibytes（`64 * 1024 * 1024` bytes） |
| `1Gi` | 1 gibibytes（`1024 * 1024 * 1024` bytes） |
| `128M` | 128 megabytes（`128 * 1000 * 1000` bytes） |

{{< keypoint >}}
注意区分 Mi（mebibyte, 1024^2）和 M（megabyte, 1000^2）。Kubernetes 使用 Mi/Gi（二进制单位）。
{{< /keypoint >}}

## 2. 压缩资源 vs 不可压缩资源

| 类型 | 资源 | 不足时行为 | 管控方式 |
|------|------|-----------|---------|
| **可压缩资源** | CPU | Pod "饥饿"（性能下降），不退出 | cfs_quota 限上限，cpu.shares 按比例分 |
| **不可压缩资源** | 内存 | Pod 被 OOM Kill | memory.limit_in_bytes 硬限制 |

---

## 3. cgroups 如何实现资源限制

### 3.1 CPU

kubelet 将容器的 CPU 资源转换成 cgroup 配置：

| requests.cpu | limits.cpu | cpu.shares 值 | cpu.cfs_quota_us 值 |
|-------------|-----------|-------------|-------------------|
| 250m | 500m | `(250/1000)*1024 = 256` | `(500/1000)*100ms = 50ms` |
| 1 | 2 | `(1/1)*1024 = 1024` | `2 * 100ms = 200ms` |
| 不设置 | 不设置 | 1024（默认） | 不限制 |

- `cpu.shares`：按权重分配 CPU 时间。值越大，在 CPU 争抢时分配到的时间越多。
- `cpu.cfs_period_us`：固定 100ms（100000μs）。
- `cpu.cfs_quota_us`：每 100ms 周期内，容器可用 CPU 时间的上限。

### 3.2 内存

| limits.memory | cgroup 参数 |
|-------------|------------|
| 128Mi | `memory.limit_in_bytes = 134217728` |
| 不设置 | 不限制 |

## 4. QoS 模型

K8s 根据 requests 和 limits 的设置，自动将 Pod 分为三个 QoS 类：

| QoS 类 | 条件 | OOM 优先级 | 典型场景 |
|--------|------|-----------|---------|
| **Guaranteed** | 每个容器都设置了 requests == limits（CPU 和内存） | 最低（最后被杀） | 数据库、核心服务 |
| **Burstable** | 至少一个容器设置了 requests 或 limits，但不满足 Guaranteed | 中 | 普通 Web 服务 |
| **BestEffort** | 没有任何容器设置 requests 或 limits | 最高（最先被杀） | 批处理、低优先级任务 |

### 4.1 判断规则

```
Pod 中每个容器都设置了 CPU 和 Memory 的 requests 和 limits
  └─ 且每个容器的 requests == limits？
       ├─ 是 → Guaranteed
       └─ 否 → Burstable
Pod 中至少有一个容器设置了 requests 或 limits → Burstable
Pod 中没有任何容器设置 requests 或 limits → BestEffort
```

### 4.2 OOM Score

K8s 通过 Linux `oom_score_adj` 实现 OOM 优先级：

```bash
# Guaranteed Pod：oom_score_adj = -998
# Burstable Pod：根据实际使用量动态计算
# BestEffort Pod：oom_score_adj = 1000（最高优先被杀）
```

{{< keypoint >}}
内存超限时，OOM Killer 按 BestEffort → Burstable → Guaranteed 的顺序杀 Pod。Guaranteed 的容器除非用到宿主机内存耗尽，否则不会被 OOM Kill。
{{< /keypoint >}}

## 5. cgroups 层次结构

```text
/sys/fs/cgroup/
├── cpu/
│   └── kubepods/
│       ├── pod<uid>/          # Guaranteed Pod
│       │   └── <container-id>/
│       │       ├── cpu.shares
│       │       └── cpu.cfs_quota_us
│       └── burstable/         # Burstable Pod
│           └── pod<uid>/
│               └── <container-id>/
└── memory/
    └── kubepods/
        ├── pod<uid>/          # Guaranteed Pod
        │   └── <container-id>/
        │       └── memory.limit_in_bytes
        └── burstable/         # Burstable Pod
            └── pod<uid>/
                └── <container-id>/
```

## 6. 实际调度中的资源计算

调度器在调度一个 Pod 时：

```text
1. 计算 Pod 的 requests 总和 = sum(每个容器的 requests)
2. 对每个候选节点：
   已用资源 = sum(该节点上所有 Pod 的 requests)
   可用资源 = 节点 Capacity - 已用资源
   如果 Pod.requests ≤ 可用资源 → 节点通过过滤
3. 注意：调度器只看 requests，不看 limits
```

这意味着：节点的实际利用率可能远超 requests 的总和（因为 limits > requests），这就是资源超卖的基础。
